### Replaying the stock Windows controls

Run the driver from the source checkout with Python 3.11 or newer and Git. Set `PKG` to the directory containing the matching release executable, and choose a work directory that does not yet exist on each run. The driver checks the executable hash, measures control positions from the fixture, and writes invocations, per-trial observations and the exact-key TSV.

```powershell
py -3 tools/dev/gesture_sweep_0640.py --list
py -3 tools/dev/gesture_sweep_0640.py --package $env:PKG --work "$env:TEMP/0640-replay" --receipt "$env:TEMP/0640-receipt.json" --evidence "$env:TEMP/0640-evidence.tsv"
```

A driver can exit successfully after producing partial evidence. After a full run, check the JSON receipt and per-key TSV. The first driver must verify all 136 trials and produce 95 distinct end-state keys. The second must verify all 107 trials and produce 107 distinct end-state keys. The frozen audit records both totals.

For a native regression case, run the source-matched `blendity_tests.exe --group <group>` with `BLENDITY_TEST_FILTER` set to the fixture substring in the row's workload. Use a fresh project, cache, temp, preferences and trash for every process. Check the named fixture and a nonzero check count in the log. The native batch manifests retain the group, filter, return code and number of checks for every invocation, including cases that corroborate a workflow without establishing a new end-state row.

### Replaying the Linux Wheel controls

Use the dependency-free Linux release objects built from the matching product source in a clean build directory. The probe supplies its own entry point. Run the following from the repository root with Bash, with `bank` set to that build's absolute `obj_release_linux` directory. Each case selects the Scene view and checks its Wheel context. The first opening closes with Space. The second selects a leaf with a number key and checks the resulting property.

```bash
out=$(mktemp -d)
objects=()
for obj in "$bank"/{src_,extern_}*.o; do
    [[ ${obj##*/} == src_app_main.cpp.o ]] || objects+=("$obj")
done
c++ -std=c++17 -pthread -O2 -DNDEBUG -I. tools/gesture_wheel_0640.cpp "${objects[@]}" -lX11 -ldl -static-libstdc++ -static-libgcc -o "$out/probe"
cd "$out"
for key in TMPDIR BLENDITY_PROJECT BLENDITY_TRASH BLENDITY_CACHE_DIR BLENDITY_PREFS_DIR; do
    mkdir "$key"
    export "$key=$out/$key"
done
BLENDITY_VIEWPORT_DEVICE=cpu BLENDITY_LIVELINK_AUTOSTART=0 ./probe
```

The same Linux release objects can link `tools/gesture_inspector_0640.cpp` and `tools/gesture_bindings_0640.cpp` in place of the Wheel source above. Run the Inspector executable without arguments to exercise the registered components, with `--stacks` to exercise camera filters and texture layers, or with `--materials` for the five surface types and additional shading models. A component display name can also restrict a run. Run `--contexts` for the Stylize menu section, numeric Frame edit and mesh and point-cloud controls. Use a fresh fixture directory for each invocation. Lines beginning with `FIELD`, `COMPONENT`, `STACK` or `BINDING` identify individual positive and control comparisons. A `MISS`, `CONTROL` or `MISSING` row requires investigation before using it as evidence. Run the additional Windows cases with `tools/dev/gesture_palette_0640.py` using the same package and a different work, receipt and evidence path.

### Reading the results by input route

The Window menu and palette window checks inspect the active serialized tab. Keyboard focus requires a separate assertion about which pane receives the next event. A palette creation result checks the saved scene or mesh against a reference and checks the starting scene against the outside click. A palette row primed in Recents covers clicking that exact name. It provides no evidence for typed search.

Three selection-mode entries have two source declarations for the same physical button. The generic transform-strip declaration covers five individually checked tool buttons. These four overlaps remain identifiable when counting source keys. A change to a similarly named menu, command, binding or Wheel entry requires its own input and witness.

### What needs hardware or external software

| Family | Reproducible on a software fixture | Outcome with an external dependency |
|---|---|---|
| VR, tablet and display | Injected tracking/pressure/posture, controller logic, VR settings, monitor layout and menu enablement | Starting a native OpenXR session through VR View or `vr start`, tracked headset output, delivery from a physical pen and actual mixed-DPI monitor placement |
| Live Link | Local server and client, discovery cleanup, inbox snapshot, plugin file/configuration installed into Unity, Godot or Unreal fixture projects | Each named engine loading the plugin and applying an update. Enabling the Blender bridge also executes installed Blender |
| Import and export | Representative Unity/Source files, procedural assets, snapshots and exported scene files can be validated and reopened locally | Actual `.blend` conversion executes Blender. Engine-side interpretation of the exported file requires that engine |
| Rendering and optional packages | Local camera, settings, refusal paths, editor output and CPU references | MoonRay execution, FFmpeg encoding, installed model execution and GPU-device output each need their particular runtime or device |
| Native dialogs and updates | Cancel, selected path and clean refusal under control of an isolated desktop/project | OS file pickers need a desktop session. A completed update needs a disposable install and a real package or controlled service |

Hardware is an outcome-level requirement. One entry can support both software checks and a physical-device follow-up. The register keeps a gap when its named result has only indirect evidence.
