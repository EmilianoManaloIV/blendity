# Raspberry Pi 5, 8 GB: where to spend the first profiling session

Round 596. The historical desktop benchmarks use the project's Windows 11 AMD64 development machine, Ryzen 9 5900XT with 32 logical cores and an RTX 4070 SUPER for GPU rows. These historical runs used the release build with Blender libraries. The current Linux ARM64 dependency-free build selects the CPU viewport. No local Pi trace or V3DV driver report was available; clock scaling a desktop result would not establish the Pi's frame time. [Machine](../handoff/MACHINE.md) · [Recorded baseline](../../stress/results/baseline.md)

## Ranked findings

1. **Establish a usable CPU viewport first.** The desktop CPU working-scene orbit took 8.03 ms/frame, of which the Scene view consumed 5.83 ms. Moving an object redrew three views and took 15.44 ms. The same move took 4.89 ms on the RTX. Try one Scene view at Low, then add the Game view and camera preview one at a time. The project's existing eight-thread CPU comparison on 200 icospheres at a 1600 × 1000 window measured High → Low orbit at 14.37 → 7.06 ms and move at 36.11 → 15.49 ms (fastest of four runs). Low already scales 3D to 67% per dimension and caps shadow size at 1024. Project targets for a low-power laptop are 16.7 ms for orbit and 33 ms for editing. Keep the longest frame beside the median to reveal delays over the 50 ms responsiveness budget. Pan needs its own measurement. [CPU and GPU frame breakdown](../../stress/results/baseline.md#editor-frames-in-a-working-scene) · [Tier comparison](../PERFORMANCE.md#pass-8-the-minimum-machine-task-0050-adr-0026) · [Responsiveness budget](../decisions/0105-responsiveness-budget.md)
2. **Check Vulkan limits before spending time tuning shaders.** Linux enables the Vulkan backend through the optional headers and shaderc library. Discovery excludes CPU Vulkan devices, requires a compute queue and accepts API 1.1 or later. Raster initialization also needs a graphics queue. Common shader compilation targets Vulkan 1.2 and SPIR-V 1.4. The main pass uses **six simultaneous color attachments**, including four RGBA16F and two R32_UINT, plus D32 depth. The common descriptor layout makes 26 storage buffers and 15 combined image samplers visible to the fragment stage. Compare the actual driver's API/SPIR-V support, attachment limits, image formats and per-stage descriptor limits against these values. A four-attachment implementation cannot run that pass. Geometry shaders enable face highlighting and the baked pass; dual-source blend enables a see-through path. Hardware ray query is optional and shadows can use a map. Linux window presentation additionally needs Xlib surface support and a compatible swapchain. Check the selected device, backend and refusal log for each tested scene. Prioritize a clear preflight/refusal for an unsupported layout before considering a smaller attachment or descriptor layout. [Build selection](../../build.sh) · [Device enumeration and shader compilation](../../src/render/gpu_device.cpp) · [Raster initialization, make_layout and make_render_passes](../../src/render/gpu_raster.cpp)
3. **Measure the Textures window's first frame separately from scrolling and picture decoding.** On the same desktop (headless editor UI, harness default CPU viewport; the row omits an actual-device field), 10/200/2,000 procedural texture assets cost 14.2/37.5/272.7 ms on first open, then 1.6/1.4/2.6 ms on the next frame. At 2,000 assets the panel exceeded its 100 ms action budget. The UI recursively enumerates asset paths, loads every procedural texture to obtain its name, and rebuilds the filtered list on redraw. Time the scan, the uncached asset loads and visible thumbnails separately. A first candidate is deferring loads of offscreen assets while preserving name-based search, selection, order and file-change visibility. The separate 4096-pixel picture-open row took 30.4 ms after round 508. A cold launch of the editor with its scratch project took 492.8 ms (three presented frames then exit, mean of three on the desktop GPU). No general startup budget follows from this wall time. [Panel rows](../../stress/results/baseline.md) · [Texture window](../../src/editor/texture_window.cpp) · [Image-editor verification](verify-511.md) · [Startup benchmark](../PERFORMANCE.md)
4. **Separate full-window presentation from 3D and editing work.** Linux's CPU full-present path copies four bytes per pixel into an XImage then calls XPutImage and XFlush. At 1280 × 720 the copy payload is 3.52 MiB/frame; at 1920 × 1080 it is 7.91 MiB/frame. At 60 full presents/s that is 211 vs 475 MiB/s of payload even before the X server transfer. Partial presents copy only the specified row bands. A headless trace skips desktop presentation, and XFlush alone does not measure display latency. Compare an actual window with the headless fixture before changing the rasterizer. An existing desktop 50k-face CPU vertex drag took 18.01 ms; the RTX path took 6.91 ms. Selecting linked from one face of a 50k-face sphere took 8.61 ms (5.10 ms in the operator). A headless 50k-face triangulate undo was 4.42 ms (operator alone 0.08 ms). Profile the frame restoring the view and the next redraw as well as the undo operation. Text save/load of 1,000 shared cubes took 2.0/6.3 ms on desktop storage (serializer timings, excluding presentation). Repeat save/reopen on the storage intended for the Pi. Count allocation events separately if a trace is available. Plane counts and model-accounted bytes above do not establish how often a general allocator runs. A Pi acceptance report should distinguish the visual result, active backend, frame distribution, first-use stalls and memory headroom. [Pi acceptance procedure](0578-pi5-acceptance.md)

### Native Linux ARM64 result

A four-vCPU Neoverse-N2 GitHub runner (Ubuntu 24.04, GCC 13.3) built the release app, tests and stress binary through `build.sh` with optional libraries and OptiX disabled. The owner approved installation of the missing X11 development package on that disposable runner. `readelf` identified the application as AArch64. The headless CPU viewport rendered a 1280 × 720 PNG after adding 64 cubes, and the editor and input groups passed 4,101 checks. [Native ARM64 run and artifacts](https://github.com/EmilianoManaloIV/blendity/actions/runs/44583737244)

The single Low-tier smoke process took 0.13 s including launch, scene setup, rendering, PNG encoding and exit, with 60,076 KiB peak RSS. Its scene contained 71 objects, 1,051 vertices and 900 faces. Inside the process, the memory report attributed 20.0 MiB to shadow maps, 5.0 MiB to view planes and 1.7 MiB to view pictures. The job exercised CPU rendering without a display server. Pi silicon, the X11 presentation path and the VideoCore driver still require the board test.

### Windows 720p editing journey

Window 08 recorded one exclusive sample on the Ryzen 9 5900XT, Windows 11 x64 build 26200, with MSVC 19.51, Blender libraries and tbbmalloc. The staged executable came from source `22ead0eb6f953a2006d17813e94ae0da3f5bb1b7`; its SHA-256 matched the manifest (`77efd1abc32c67f32f84bd524e61ca8cf4e3ac7a418f27211ddde0c95ad034e2`). The window verified 62 quiet seconds before its first workload and reported zero build/test overlaps. Both the probe and window completed successfully. [Reproduction script](../../tools/dev/pi5_host_probe.ps1)

The two processes used the headless CPU viewport. Launching and writing the starter PNG took **145.0 ms** and reached an observed **57.4 MiB** peak working set. The complete Low-tier editing journey took **322.6 ms** and reached **99.3 MiB**, including setup, writing the PNG and exit. The probe sampled the OS-reported peak while each process was alive at 10 ms intervals.
