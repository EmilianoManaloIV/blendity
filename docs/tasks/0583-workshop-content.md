## Goal and ownership
Select an installed item folder, loose entry or multipart VPK. Resolve map-embedded content first, followed by ordered user mounts. Return the chosen virtual path and its provider.

Owned paths or surfaces: src/scene/source_content.*, editor import picker and import dispatch, shared build registration, src/editor/lessons.cpp. Coordinate registration and shared interface changes through the mounting round.

## Acceptance and verification
A two-model folder lists both paths. Reimport keeps same-named material and texture identities when their order or cached bytes change. Moving an item retains edits when its Workshop IDs and provider chain match, or when a non-Workshop source has unique selected-entry evidence. Separate Workshop items stay separate even when their virtual paths and entry bytes match. Legacy migration retains dormant filename candidates across restarts and leaves ambiguous files intact. Duplicate paths resolve by mount order. Adding a second root satisfies a named missing dependency. Cancel leaves the scene intact. An item may contain a map VPK inside a multipart outer VPK. Discover and read it using bounded indexes and lazy payload reads, keeping outer material dependencies available. Exercise duplicate names and actionable diagnostics on a corrupt or unsupported child. Verify Workshop item 3070193546 alongside synthetic fixtures. Derive independent tests from these criteria. ## Implementation and provenance

- Candidate based on Blendity `f83be355fd22a4a59317227d9eff78a0e1df92df`. The File menu and `import source` open the same picker. An additional root is searched after the item and earlier roots; a new primary item resets that list. Loose-file selection infers the root above `models/` or `maps/` when present. Map readers can prepend an embedded package on a copy of the resolver. Directory enumeration and conversion run on a worker in the editor.
- Workshop delivery follows the [Steamworks local item installation workflow](https://partner.steamgames.com/doc/features/workshop/implementation#ItemInstallation). Valve's [Source SDK BSP header](https://github.com/ValveSoftware/source-sdk-2013/blob/e1f1fd42271805072f052051c26c21caa2c87b04/src/public/bspfile.h) identifies the embedded pakfile lump. [ValvePython's VPK implementation](https://github.com/ValvePython/vpk/blob/3ff641e5fa7cf53a12c886153db0aab7a7872821/vpk/__init__.py) documents the interoperable v1/v2 tree, inline preload data and numbered archives. [PKWARE ZIP APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) specifies the ZIP records and compression methods used for stored/DEFLATE BSP members.
- Parser limits cap individual decoded resources at 512 MiB, VPK trees at 64 MiB and individual indexes at 250,000 entries. Virtual paths are case-insensitive in ASCII and validated before lookup. Archive bytes stay in memory or in their mounted file and are never extracted to a path taken from an archive.
- Nested VPKs keep their own provider chains. Selecting one searches that package and its ancestors before the remaining ordered mounts. Sibling archives cannot supply dependencies for that selection. A matching directory VPK identifies numbered chunks even when the first payload starts with a VPK signature. The picker reports malformed archives discovered inside folders and nested packages while retaining accessible loose files and healthy siblings.
- Nested headers and indexes are read as bounded ranges over their containing entry. Payloads are fetched only when requested, including across VPK preload bytes or numbered chunks. The selected inner resource's CRC is checked. Index budgets are 64 MiB per VPK directory tree and 256 MiB of raw index and normalized lookup keys across the mounted VPKs, with 1,000,000 aggregate entries, at most 256 discovered physical packages per folder, 128 nested package attempts per scan, and four nested levels.
- Converted textures use the normal project texture pipeline. The import cache respects a nonempty `BLENDITY_CACHE_DIR` so an isolated run can remove the cache and check reopen. The worker stages converted files in a disposable directory under the starting project. The main thread checks the project and scene again before publishing fresh assets, writes the source marker last, and rolls back files and directories it created if publication fails. A canceled picker discards its stage before any publication. Existing edited materials and textures are reused.
- Readers supply origin-relative material and texture identities plus semantic variants through `ImportResult`. Project-local records keep each native filename tied to that identity. Snapshot provider records distinguish Steam app and item IDs and the provider chain relative to the item directory. For other installations the resolver records the selected VPK member CRC and length, or hashes the selected loose file on the read worker. A unique matching fingerprint and unavailable previous provider are required to reuse a non-Steam snapshot after moving. Exact provider reimports keep edits even after updates. Legacy migration records the original regular material and texture filenames once, including assets absent from an intervening import. Later imports only consider those recorded filenames and their earlier claims. Source groups with ambiguous legacy names retain the existing files and show an import diagnostic.
- The editor publishes staged files without a copy on its thread. A hard link is used where supported, or the same-volume exclusive rename primitive on [Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Linux](https://man7.org/linux/man-pages/man2/renameat2.2.html) and [macOS](https://devstreaming-cdn.apple.com/videos/wwdc/2017/715gk347h3udl/715/715_whats_new_in_apple_file_system.pdf?dl=1).
- Implementation uses no copied game assets. Independent synthetic fixtures and per-title provenance belong to the test-engineer and verification rounds.
